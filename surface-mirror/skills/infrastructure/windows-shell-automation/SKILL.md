# Windows Shell Automation
Use when executing PowerShell commands through the `terminal` tool within an MS/bash environment on Windows hosts.

## Shortcut (.lnk) Rewiring
When the drive letter a NEXUS CORE / TESSERACT .lnk points at changes, patch **both** the `WorkingDirectory` and the `TargetPath`/script `Arguments` — a shortcut whose workdir is still on the old letter silently fails to launch and leaves a ghost app on the taskbar. Fix by writing each .lnk object via `WScript.Shell.CreateShortcut` and `-replace '^Q:', 'E:'` to both fields, then `.Save()` back to the same path.

## Remote Windows Node Administration (SSH + SMB file transport)

Administering a Tailnet Windows node over SSH adds a third quoting layer (bash → ssh → cmd/PowerShell) on top of MSYS. Rules:

* **Never inline remote content containing `$`** — a `$` in the remote username (e.g. `CHANN0$`) or in remote paths (`C:\Users\CHANN0$\...`) shreds every inline quoting scheme, and even base64 `-EncodedCommand` payloads arrive truncated. Instead: copy scripts to the node's SMB share (`cp script.ps1 //<host>/<share>/`), then execute by path over SSH: `ssh '<user>@<ip>' "powershell -NoProfile -ExecutionPolicy Bypass -File C:\project\script.ps1"`. Only a `$`-free path crosses the layers.
* **Remote command chaining uses `&&`, never `;`** — semicolons get eaten by the ssh→cmd layer and collapse the chain into argument noise.
* **Processes started from an SSH session die with the session** — `Start-Process` children are torn down at disconnect. For anything persistent use `Register-ScheduledTask` (the PowerShell API, NOT `schtasks /create`, whose CLI quoting mangles task definitions) with a wrapper `.cmd`, trigger AtLogOn, then `Start-ScheduledTask` to fire it immediately.
* **Machine-scope env changes do not reach already-running user sessions** — a per-user tray app keeps its startup-time env snapshot and will respawn a conflicting instance (e.g. ollama bound to 127.0.0.1 after you set OLLAMA_HOST machine-wide). Make wrapper scripts idempotent: `taskkill` the stale instance first, then start yours with all env vars set inside the wrapper itself.

## Pitfalls
* **Hermes `terminal()` strips `=` from PowerShell assignments in `-Command` strings.** When the `terminal` tool forwards a `powershell -Command "..."` argument, any `=` inside the PowerShell body gets stripped before reaching PowerShell, breaking every multi-statement script (`$sc = ...; $sc.Save()` becomes `New-Object ...  .Save()` with the assignment part collapsed away). Symptom: PowerShell sees a partial command starting with `= ` and errors with `The term '=' is not recognized as the name of a cmdlet`. The same stripping is silent on long paths and complex expressions.
  - **Fix:** do not try to write multi-statement PowerShell inline through `terminal()`. Three options, in order of reliability:
    1. **Write the script to a `.ps1` file first** (with `write_file` — not `echo >`), then run `powershell -ExecutionPolicy Bypass -File "<path>.ps1"`. The script's `=` characters are inside the file, not inside the terminal's command argument, so they survive.
    2. **Wrap the PowerShell call in `execute_code` Python** using `subprocess.run(['powershell', '-Command', ps_string])`. The Python string lives inside `execute_code`, not inside the `terminal` tool's command parameter, so the `=` characters are protected from the stripping.
    3. **Use a single-line cmdlet** (e.g., `(New-Object -COM WScript.Shell).CreateShortcut('x').Save()`) where possible. This avoids assignments entirely.
  - **Diagnostic:** if you see `The term '=' is not recognized` from PowerShell and your script clearly had assignments, do not retry with different escape sequences. The strip is at the terminal layer, before PowerShell ever sees the string.
* **Multi-`taskkill` under MSYS**: a single `taskkill //PID a //PID b //F` returns `ERROR: Invalid argument/option - '//PID'.` — the second PID token is mangled by MSYS path translation. Issue one `taskkill /PID N /F` per process, chained with `;`.
* **Path Misinterpretation**: Avoid using bash-style paths (e.g., `/c/Users/...`, `$HOME`) or unquoted variables in PowerShell strings passed from Bash. The shell wrapper may intercept or incorrectly translate these before they reach the PowerShell engine. Always prefer native Windows environmental primitives like `$env:USERPROFILE`.
* **Property Access Failure**: Do not use complex property access or interpolated objects (e.g., `$_.Length`) inside single-line command strings. The interaction between the MSYS2 parser and the PowerShell string can cause `ParserError` due to unhandled dot operators and parentheses.
* **Parens in double-quoted PowerShell strings**: `Write-Host "click here (or there)"` fails with `The string is missing the terminator: ".` PowerShell treats `(` inside `"..."` as the start of a subexpression. Use dashes or escape with backticks: `` `( `` . Same goes for nested `${...}` blocks inside double quotes.
* **Apostrophes inside single-quoted PowerShell strings**: An English-style apostrophe like `Ctrl+Alt+N's hotkey` inside `'...'` terminates the string. Use double-quoted strings, or double the apostrophe: `'N''s hotkey'`.
* **`cmd.exe /c` under MSYS bash**: `cmd.exe /c "call start.bat"` errors with `The syntax of the command is incorrect` because MSYS path-translates `/c`. `cmd.exe //c "start.bat"` opens an interactive cmd prompt instead of running the script. Skip `cmd.exe` for `.bat` scripts — launch `.ps1` with `powershell.exe -ExecutionPolicy Bypass -File`, or use a Python wrapper (`python script.py`).
  - **Exception: `cmd /c "..."` to survive Hermes shell-wrapper close.** When the goal is to detach a long-running process (dev server, watch loop) so it survives the parent `terminal()` call exiting, wrapping the command in `cmd /c "..."` is the right move — the process becomes a child of `cmd.exe`, which the MSYS bash wrapper does not track. Symptom of getting this wrong: every reported background exit shows `exit 1` with `stdin is not a tty` because the bash process SIGTERM'd the child on close. See `throne-windows-adaptation` for the full pattern.
* **UTF-8 BOM in PowerShell scripts**: When a `.ps1` is written by a tool that emits a UTF-8 BOM (`EF BB BF`), PowerShell sometimes garbles the parse and fails on line 1 col 1 with no real reason. Strip the BOM when saving a `.ps1` you intend to invoke, or write ASCII-only content.

* **Path/Identity Mismatch (The 'CHANN0$' Trap)**: If searching for files or credentials on a multi-node Tailnet (e.g., SHADOW looking for MSI), do not assume the current shell's environment (`$USER`, `$HOME`) matches the target node's identity. Always verify which host you are physically logged into via `hostname` and check if your search path is relative to your *local* disk or the *remote* one! Verify connectivity with `ssh <alias>` before assuming local file paths exist on remote nodes.

* **Hermes `terminal()` shell is not elevated** — `reg add HKLM\...`, `Set-ItemProperty HKLM:\...`, `Set-CimInstance Win32_PageFileSetting`, and `powercfg` writes all return `PermissionDenied` or `Requested registry access is not allowed` from this shell, even when the user is an Administrator. HKCU writes work. Plan ahead: HKLM system-wide tweaks (NVIDIA PowerMizer class key, pagefile on a second drive, Group Policy keys under `HKLM\SOFTWARE\Policies\...`) need a manual GUI step or a scheduled task running as SYSTEM with `psexec -s -i` (rarely present). Detect this on the first failed write and switch to "manual steps" mode rather than retrying with different syntax — the constraint is elevation, not command shape.
* **`cmd.exe //c` opens an interactive prompt** under MSYS2 — the command never runs. `cmd.exe /c` path-translates `/c` to `C:\c`. Skip `cmd.exe` entirely for most purposes. Use `powershell.exe -NoProfile -Command` for Windows diagnostics (Get-Process, Get-Service, Get-NetTCPConnection instead of tasklist/sc/netstat).
* **Node.js paths inside single-quotes also mangle.** `'/c/Users/.../node.exe' '/c/Users/.../index.js'` becomes `C:\\c\\Users\\...`. Use `cmd.exe /c "C:\\path\\to\wrapper.cmd"` (full Windows path, no MSYS slashes inside) to launch Node-based tools.

* **`terminal()` hardline blocks oversized/heredoc-style commands.** The `terminal` tool parses the `command` parameter and refuses to run what it considers an unparseable payload — large one-liners with pipes, backticks, embedded `\n`, or heredocs trigger: `BLOCKED (hardline): command parser limit or malformed executable payload ... If you genuinely need to run it, run it yourself in a terminal outside the agent. RECOVERY: this block fires on oversized/unparseable inline command payloads (heredocs, giant one-liners), not on the operation itself. Your command was saved to ...\blocked-scripts\blocked-<ts>-<hash>.sh — review it, then run: terminal(command="bash <path>"). Do not retry inline.`
  - **Fix:** split the work into smaller commands (one `cd` / `mkdir` / `pip install` at a time), or shell out via `execute_code` + `subprocess.run()` to run the full command. The blocked-script path is a real shell script you can run later; it's not a feature to lean on because the path rotates per call.
  - **Diagnostic:** if you see the `BLOCKED (hardline)` text in tool output, do not try to work around it by tweaking escaping. The block is content-shape based, not parse-recoverable.

* **`grep`/`rg`/`find`/`sed`/`cat`/`echo >` are deprecated inside the `terminal` tool.** The tool description says "do not use cat/head/tail (use read_file), grep/rg/find/ls (use search_files), sed/awk (use patch), echo/heredoc file creation (use write_file)." When a tool result shows blocked output like `These tools are not available in this context`, fall back to `read_file` for reads, `search_files` for search, `patch` for in-place edits, and `write_file` for new files. Compose commands out of those primitives instead.

* **MSYS bash heredoc append `cat >> file << 'EOF' ... EOF` silently swallows the EOF and exits non-zero when the body contains both `'` and `"` characters.** A single-quoted heredoc (`<< 'EOF'`) is supposed to disable all shell expansion inside the body, so apostrophes, double quotes, and backticks inside the body are supposed to pass through verbatim. In MSYS bash, this contract is *not* honored once the body contains a `'` character: the parser starts looking for a matching closing `'` to balance the opening single quote of the `<< 'EOF'` marker, finds one mid-body, and bails with `bash: -c: line N: unexpected EOF while looking for matching "'"`. The exit code is 2. **The trap:** in many cases, the heredoc has already been streamed to the target file before the parser error fires — `tail -5 file` shows the full content wrote. A caller that trusts the exit code will re-run the same heredoc and double-write the content; a caller that trusts `tail` will move on. The fix is to never trust the exit code from a single-quoted heredoc append on MSYS: either verify the file with `wc -l` / `grep` and de-dup if needed, or skip bash heredoc entirely. **Skipping the failure:** for any file append whose body contains BOTH apostrophes and double quotes (a markdown document quoting both English and Latin terms, a Python/JSON payload, a citation table), use `execute_code` + `with open(path, 'a', encoding='utf-8') as f: f.write(content)` instead of bash heredoc. The Python `open` call is not subject to MSYS shell parsing, the file mode is explicit (`'a'` append), and the exit semantics are reliable. This pattern landed 3+ times in the G08 dossier cycle (WORK_LOG appends with `'Stargate'`, `'Sendivogius'`, and similar) — bash heredoc returned exit 2, Python open wrote cleanly. Default to Python open for any non-trivial file append on MSYS.
